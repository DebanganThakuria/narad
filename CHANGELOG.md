# Changelog

All notable changes to Narad are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Versions below 1.0.0 (the `alpha` and `beta` tags) were pre-releases and are
summarized more briefly than the 1.x and later entries.

## [Unreleased]

### Added
- This changelog, covering every release back to the first alpha.
- `MAINTAINERS.md`, stating who reviews changes, what a single-maintainer project means for review turnaround and bus factor, and how to become a maintainer.
- Container images are signed with Sigstore cosign (keyless, no long-lived key) and carry an SBOM and SLSA build provenance. This starts with the first image built after the v3.0.1 release; verifying an earlier tag fails because those images were published without them.
- A `govulncheck` job in CI, run on every pull request and weekly against the latest vulnerability database, so an advisory against a dependency surfaces without waiting for a code change.
- `scripts/check-release-refs.sh`, wired into `make check` and CI, which fails when a pinned image tag in the documentation has drifted from the newest release tag.
- A nightly linearizability check. A three-node cluster takes load while nodes are killed and cut off from their peers on the cluster plane; every client operation is recorded with the interval it was in flight for, and the history is checked against a sequential specification of the delivery contract. A message redelivered after a confirmed ack now has to sit inside a fault window, and one that does not fails the run. A second leg injects no faults and runs strict, which asserts that a healthy broker never redelivers an acked message.
- The load driver records an operation history with `--history`, in a format shared with the checker (`tests/linearizability/history`).
- Documentation for all of it, including what the check cannot catch: [Checking the Delivery Contract](docs/understand/linearizability.md).
- A [Go SDK](https://github.com/DebanganThakuria/narad-go) in its own repository, depending on nothing but the standard library, with a guide on the documentation site. Three calls cover almost everything, and the consumer handles the visibility lease: it renews the lease while a handler runs, cancels the handler if the lease is lost, acks on success and hands the message back on failure.
- `storage.consumer_offset_commit_interval_ms` (default 1000, 10 to 60000, settable in the config file): the durability interval of acked consumer frontiers and out-of-order ack sets. Every 100 ms (or every interval, when that is shorter) each partition acked since the last tick has its state written into the page cache, and once per interval each of those partitions is synced to disk (see Performance). A crash of the broker process redelivers about 100 ms of acks, and a power loss, kernel crash or instance loss up to about the interval plus 100 ms and the sync time, about 1.1 s at the default; v3.0.1 redelivered about 0.1 s plus the time its sync took after either. Setting the key to 100 restores the power-loss window of v3.0.1. The offset committer used to run on the storage flush interval, so the two could not be tuned apart. See [Configuration](docs/reference/configuration.md#consumer-offset-commit-interval) and the upgrade notes below.
- `storage.ingress_wal_prealloc` (default `false`, settable in the config file): prepares ingress WAL segments ahead of use so a group commit's `fdatasync` no longer commits the inode through the file system journal. Off by default because it changes crash recovery and rollback; see the upgrade notes below and [Configuration](docs/reference/configuration.md#ingress-wal-segment-preparation).
- The `narad_ingress_wal_failed` gauge: 1 once a write or sync of the node's ingress WAL has failed and produce is latched off until a restart, else 0. Consume and `/readyz` are unaffected by that latch, so this gauge is the signal to alert on.
- Batch consume: `GET /v1/topics/{topic}/consume?max=N` (N from 1 to 100) answers `{"messages":[...]}` with up to N messages, each exactly as a single consume returns it, with its own receipt handle and visibility window, or `204`. On a node that owns some of the topic's partitions the messages come from one scan of them. Only when that finds nothing does the request go to the other owners, asking for up to N in its opening probe and in its long-poll's token claim alike, and pass the owner's batch through; a message the node's own partitions deliver during the wait is topped up by a second scan of them. An owner on an earlier release still answers with one message, which goes out alone from the opening probe and is topped up by a second scan of the node's own partitions when it came from the wait. A node that owns none of the topic's partitions (or not the pinned one) forwards the request asking the owner for up to N, from its opening probes and from its long-poll wait alike (the token claim, the 2 s re-probe and the polling fallback), and passes the owner's batch through: over loopback QUIC on macOS, batches of 100 cost about 1.35 µs per record against 45.8 µs forwarded one at a time. A request is never held to fill N, nor filled from several owners, except by that top-up. One scan stops reserving once the keys and payloads it has taken reach 4 MiB (the record that crosses the bound is kept), and a response carries at most 8 MiB of encoded messages, the first always included; messages left out, which in practice only text inflated by JSON escaping causes, are nacked at once for the next consume, so they show as nacks and are counted as consumed again when redelivered. `max` does not combine with `offset`. See [Consuming in batches](docs/build/consuming.md#consuming-in-batches). A batch consume must send an `X-Narad-Client` header (any value; the CLI and the Go SDK send it) and is answered `400` without it, so a page on another origin cannot use an operator's cached Basic credentials to reserve messages 100 at a time.
- Batch ack: `POST /v1/topics/{topic}/ack` without a `receipt_handle` parameter and with a JSON body `{"receipt_handles":[...]}` (1 to 100 handles, at most 64 KiB) settles every handle on its own, with `extend` applied to all of them, and answers `200` with `{"results":[...]}`: one status per handle, in request order, each the one a single ack of that handle would have answered, with its error message when it failed. Handles other nodes own go out as one RPC per owner, the owners in parallel. The body is decoded one handle at a time and refused at the 101st (`too many receipt_handles: more than 100`). See [Acking in batches](docs/build/consuming.md#acking-in-batches).
- The `narad_ingress_dispatch_backlog_records` gauge, per node: the ingress WAL's durable next sequence minus the stored dispatch checkpoint, which is how many records a restart would replay. It is the signal to wait on before a rollback (see the upgrade notes below).
- Batch produce: `POST /v1/topics/{topic}/produce/batch` with a JSON body `{"messages":[...]}` of 1 to 100 messages, each `{"key","key_encoding","payload","payload_encoding","partition"}`, within the 1 MiB body cap of a single produce and under the produce permission. A payload is a JSON value stored exactly as written, or any bytes as base64 with `"payload_encoding":"base64"`; a key that is not valid UTF-8 goes as base64 with `"key_encoding":"base64"`; the `key` and `partition` query parameters are refused on this path. It answers `202` with `{"accepted":N}` once every message is durable, and it is all or nothing: a message that fails gets the status a single produce of it would get, its error prefixed `message <i>: `, and nothing is stored. The checks run in two passes, the format of every message (encodings, an empty payload, a negative partition) before any message's schema and partition range, so a later message's bad base64 is reported ahead of an earlier message's schema failure. The messages go into the ingress WAL in one append, in batch order (so same-key messages keep batch order in normal operation), and wait for one group commit, two when the WAL rolls a segment inside the batch. Measured at the WAL on macOS with one caller: about 51 µs per message in batches of 100 and 0.5 ms in batches of 10, against about 4.7 ms for a single produce. A timeout or 5xx is ambiguous for the whole batch, so a retry may duplicate part of it; a batch that fails after the WAL rolled a segment inside it may still have its leading messages delivered. At-least-once holds either way. The body is decoded one message at a time and refused (`400`, `too many messages: more than 100`) at the 101st, so a request costs at most a full batch however many elements its body holds. A server that predates batch produce answers `404`: fall back to single produces. See [Producing in batches](docs/build/producing.md#producing-in-batches).
- `http.max_produce_in_flight_per_identity` (env `NARAD_HTTP_MAX_PRODUCE_IN_FLIGHT_PER_IDENTITY`, default 0, off): a cap on concurrent produce requests per authenticated user, or per client IP with security off, answered `429` beyond it. A batch produce counts as its message count, clamped to the cap, and counts one from before its body is read until that count is known, so the cap also bounds the batch bodies one identity has being read and decoded. It is off by default because a produce holds its goroutine only until the ingress WAL's group commit, not for a long-poll's wait. Settable in the config file, which v3.0.1 rejects; see the upgrade notes below.
- On Linux, when `GOMEMLIMIT` is unset, `narad serve` sets the Go soft memory limit to 90% of the process's cgroup memory limit (cgroup v2 `memory.max` or v1 `memory.limit_in_bytes`, the tightest from the process's cgroup up to the root, unlimited ones ignored) and logs it once (`go memory limit set from the cgroup memory limit (set GOMEMLIMIT to override)`). Any non-empty `GOMEMLIMIT`, `off` included, always wins (an empty one counts as unset), and `GOGC` is never changed. Under the chart, `resources.limits.memory` is now enough; the chart's default sets no memory limit, so nothing is set there. See [Values that matter](docs/operate/deploy-kubernetes.md#values-that-matter-grounded-in-our-live-cluster).
- `narad_schema_validation_seconds` (histogram), `narad_schema_validations_in_flight` (gauge) and `narad_schema_rejections_total{reason}` (counter), exported by every node: the time of validations that run under the new validation bound, how full that bound is, and payloads and schemas refused by schema checks, by reason. See [Metrics reference](docs/reference/metrics.md#schema-validation).
- A node refuses to open a metadata database (`fsm.db`), or to install a Raft snapshot, that has applied a Raft entry type from a newer release. Opening one fails with `holds raft entry type <n>, written by a newer Narad release than this build ...; run that release or newer`, and the database is left untouched; installing one stops the node as below.
- Metastore and Raft metrics: `narad_raft_state`, `narad_raft_term`, `narad_raft_last_log_index`, `narad_raft_commit_index`, `narad_raft_applied_index`, `narad_raft_fsm_pending`, `narad_raft_has_leader`, `narad_raft_last_contact_seconds`, `narad_raft_voters`, `narad_raft_nonvoters`, `narad_metastore_fsm_bytes`, `narad_metastore_applied_index`, `narad_metastore_snapshot_bytes`, `narad_metastore_snapshot_duration_seconds`, `narad_metastore_snapshot_failures_total`, `narad_metastore_apply_errors_total{kind}`, `narad_metastore_apply_stalled` and `narad_metastore_apply_stopped`. They are read at scrape time without waiting on Raft, so they answer while a node's Raft is stuck. Alert on `narad_metastore_apply_stopped` = 1 (and on `narad_metastore_apply_stalled` = 1, which comes first when the disk refuses writes), on `narad_raft_has_leader` = 0 for a minute, and on `narad_metastore_fsm_bytes` growth. See the [Metrics reference](docs/reference/metrics.md#metastore-raft) and [Monitor and alert](docs/operate/monitoring.md#metastore-alerts).
- Each member's heartbeat now carries its build and the newest Raft entry type it applies, and the leader records both on the member. The leader uses a new Raft entry type only once every member of the cluster, voters, non-voters and members marked dead included, reports one that knows it, and keeps using today's entries until then, so a node on an older release never meets an entry it cannot apply during a rolling upgrade. A Raft server with no member record holds a new type back until it registers or is removed. See [Raft entry types and upgrades](docs/understand/metastore-and-raft.md#entry-types).
- A node that applies fewer Raft entry types than every recorded member, or than the newest type the cluster has already applied, is refused when it joins (`409`, code `older_release`, with both sets in the message); upgrade it to the cluster's release. A staged joiner that has not registered yet does not lower that bar. The joiner logs `cluster join refused: this node runs an older release than every member of the cluster` at error once and keeps asking every 2 s; the leader logs `cluster join refused: the joiner runs an older release than the cluster` at error, at most once a minute per joiner. A node already in the Raft configuration is never refused this way. See [Troubleshooting](docs/operate/troubleshooting.md#log-join-older-release).

### Changed
- The linearizability verdict can now fail on a broker that never finishes. `OVERDUE` used to cover any backlog and exit zero, so a broker refusing every ack left every message unacked and still passed; past `--max-overdue` the verdict is `STALLED` and the run fails.
- Fault coverage is enforced rather than only reported. Where faults cover most of the run, every redelivery is explained by construction and a clean result means nothing, so past `--max-fault-coverage` the verdict is `UNKNOWN` with that as the stated reason.
- The load driver aborts when two consumers confirm the same message concurrently. That is a double lease, and the linearizability model is untimed, so it is the only leg that can see one.
- The fault injector's spacing is derived from the visibility timeout rather than hardcoded, so a run with a longer timeout cannot overlap consecutive grace periods into one continuous excuse. The evidence floor is derived from the requested rate for the same reason: a flat floor was a fraction of a percent of what a run records.
- The nightly fails when its fault injector recorded nothing. The injector is a background process, and a run that lost it was reporting `PASS` on evidence it never gathered.
- Released images report their release version from `narad version` instead of a commit SHA.
- The formatters are pinned rather than installed at `@latest`, and CI now runs the format check. A formatter that moves version on its own reformats files nobody touched, and the first person to find out is whoever's unrelated pull request fails; a file had already drifted on `master`, so the documented `make check` failed for anyone who ran it.
- `SECURITY.md` states which versions receive fixes, target response times, and which documented configurations are out of scope, replacing a supported-versions note that still described the project as pre-1.0.
- The README carries a project status section: what the tests cover, and the three structural limits (no ordering guarantee, no synchronous replication, months of track record rather than years).
- Narad builds on Go 1.27. Building from source now needs a 1.27.1 toolchain, and the container image builds on `golang:1.27-alpine`. The pinned `govulncheck` moved with it: v1.1.4 vendors a copy of `x/tools` whose type traversal panics on the type forms 1.27 introduced, so it crashed instead of scanning. Nothing in the broker changed to accommodate the release. `encoding/json` is the one item that looked like it might, since it is now backed by the v2 implementation, but the v1 API keeps v1 semantics: duplicate object names and invalid UTF-8 decode as they always did, which is what the metastore and the Raft snapshots depend on.
- A produce without a key is stored without one. Consumers get no `key` field for it, where they used to see an invented `key-<n>`; keyless messages are now spread round-robin (the invented key used to be hashed like any other). Messages stored before the upgrade keep the key they were given. Each topic has its own round-robin rotation on each node, starting at a random partition, so a producer that writes several topics in turn still spreads every one of them evenly over its partitions. Fan-out copies a keyless message to the child partition with the same index as its parent partition when the child has the parent's partition count, so a replica child (created with `parent`) still keeps the two copies on different nodes, as the hashed invented key did; into a child with a different partition count, keyless messages go round-robin. During a rolling upgrade a node on an older release does not do this (see the upgrade notes).
- A consume response's `key` is always a valid JSON string. A key that is not valid UTF-8 comes back base64-encoded with `"key_encoding": "base64"` beside it, mirroring `payload_encoding`; `narad sub` prints such a key in hex, marked `(binary)`.
- The partition `hwm` file holds a boundary only while the log is closed: `Close` writes the exact high-watermark, the first commit after an open empties the file (at most one truncate and fsync per log open), and an empty file recovers the boundary from the CRC-verified record tail. Two consequences are visible. A crash's hidden tail (records a commit that never returned had written, fsynced or not) becomes visible when the log reopens rather than at its next commit, as duplicates the ingress WAL also re-commits. Before it takes the boundary from the tail, the open fsyncs the active segment (one fsync per partition open after a crash, off the commit path), so a power loss after the restart cannot take back a record the reopened log served. And the `hwm` file can fail a commit only until the first commit after an open has emptied it (an unusable path keeps failing commits, which the ingress WAL retries); after that commits never touch the file, and a failure to write it surfaces at `Close`. A fan-out cursor that reads a parent partition left closed in that state opens the log to drain its backlog, and the children listing, which never opens a log, leaves such a partition out until it is opened, so its child's `lag_complete` reads `false` meanwhile.
- `narad_storage_high_watermark_persist_duration_seconds` now observes at most one release per log open (at its first commit) and at most one write per close, not one fsync per commit. Its rate no longer tracks commits, so dashboards and alerts that read it as a per-commit cost no longer measure one.
- Commit batches that reach one partition together share one append and one durable commit under the produce lock, and share its outcome: a failed cycle fails every batch in it, and each is retried by the ingress WAL or the fan-out cursor as before. Once it has taken in the queued batches, a cycle checks that the partition log it resolved still belongs to the live topic, and resolves it again when a delete and recreate landed in between, so a batch for the new incarnation is never written into the old incarnation's log.
- The owner re-checks ownership, the handoff freeze, whether the caller is still waiting, and the topic incarnation under the partition's produce lock. A batch whose caller already gave up is not appended, and a batch stamped with another incarnation is refused with a retriable error.
- Commit times never decrease along a partition within one process: a batch stamped earlier than the partition's newest commit is raised to it under the produce lock. The fan-out delay gate relies on this.
- A node that owns none of a topic's partitions parks its consumers on delivery tokens instead of polling the owners, with a re-probe every 2 s as a safety net. It still polls while an owner of the topic refused a registration within the last 2 minutes (an older node during a rolling upgrade).
- Stale delivery tokens are left to lapse at their TTL instead of being dropped with a frame to every owner; consumers parking within 250 ms of a registration share it. Owners still accept drop frames from older peers.
- A queue-style long-poll on a topic whose partitions are not assigned yet, or whose owners are all down, waits out its `wait` for a route to appear instead of answering `204` at once. These held requests count against `http.max_consume_in_flight_per_identity`.
- A forwarded ack, extend or nack whose requester gave up while it queued for a handler slot on the owner is answered `503` without being applied, and a probe or claim in the same position is answered `204` (a claim's hold is retired). Produce commits have a concurrency bound of their own, the same size as the other messaging handlers' (max(64, 4 x GOMAXPROCS)).
- A produce commit whose sender gave up while it waited on the owner for one of those commit slots is answered `503` at once, without being applied, and its records are freed then rather than when a slot frees, which can take many seconds while the owner's disk stalls. Nothing else changes: the commit path refused a cancelled commit already, and the sender has stopped waiting for the reply.
- Partition transfers (segment chunks, fan-out cursor listings, handoff freezes) ride a second peer client with its own UDP socket and connection to each peer, opened on first use, so a node holds two connections to a peer it has moved partitions with.
- Any cluster RPC that ends on a deadline, not only one that hits the transport's fallback timeout, triggers a liveness ping of its connection. The connection is dropped only if the ping goes unanswered for 1 s and nothing else arrived on it meanwhile.
- A topic create or partition increase made while the cluster is still forming (some Raft voters have not registered as members) waits up to 2 s for them, so its partitions are spread instead of landing on the first node and being moved. A create or partition increase that finds no alive member at all still succeeds and now logs a warning with the error `metastore: no alive member to own new partitions`: "topic created without immediate partition assignment" for a create, "topic partitions increased without immediate assignment" for an increase. Both used to succeed without a word.
- The per-partition gauges (lag, oldest unconsumed age, in-flight and acked-ahead sizes, partition size, segments) are exported for owned partitions whose log is closed, read from disk and refreshed at most every 30 s, and a partition with no consumer state loaded reports its persisted frontier instead of 0. Three more series follow from the same change. `narad_partitions_total` and `narad_topic_bytes` are summed over those partitions, so they now count owned partitions with a closed log too and step up after the upgrade on a node with idle-evicted partitions or ones not reopened since a restart. `narad_consumer_dropped_messages` is exported for closed partitions as well, and a partition with no consumer state loaded no longer reports everything below its log start as dropped.
- A metrics poll reads each topic's incarnation marker once, not once per closed partition it rereads, and spreads the rereads of closed partitions' files over the 30 s refresh interval, so partitions read together (after a restart, or in one idle-eviction sweep) do not all come due in the same poll, where one poll in six would reread every closed partition. A partition's first refresh comes sooner than 30 s, never later, so no reading is older than 30 s.
- The fan-out cursor file (`fanout-<child>.offset`) is a fixed 256-byte, CRC-checked JSON record advanced in place with one write and one `fdatasync`, instead of a temp file and a rename per slab. Old files are read and migrated on the first advance.
- Accepted produce records for a topic with an incarnation id (any topic created on v2.2.0 or later) are written to the ingress WAL in record format 2, which adds that id. Records for an older topic stay in format 1.
- The produce dispatcher commits each destination partition on its own instead of in passes: at most one commit in flight per partition, up to 16 across partitions, each new batch carrying whatever queued while the last one ran. A failing destination holds one probe record, retried on a 5 s budget once a second, while its other records wait in the ingress WAL, and after 3 s of failed commits (it was three failed dispatch passes) its records are rerouted to a live sibling partition. Only a failure to read the WAL or store the checkpoint backs off the whole dispatcher.
- A dispatcher rescan of the ingress WAL stops as soon as every partition it could place records for is blocked again or has nothing left, so the dispatcher does not decode a hot partition's whole skipped backlog again after each of its commits. On a one-partition backlog of 131072 records it reads each skipped record again about once (0.97 times per record, against 10.75 for a rescan that runs to its lookahead horizon). A hot partition's next batch is also read from the WAL while its current commit runs, so it goes out as soon as that commit lands. Together, draining that backlog with 1 ms commits went from about 435k to 1.47M records/s on macOS, allocating 73% less. Nothing on the wire changes.
- A produce commit to another node carries each record's topic incarnation id, so the owner refuses records of a replaced incarnation the way a commit on the accepting node already did. An owner on an older release refuses the field (`400`, trailing data); it gets the batch again without the ids, and batches without them for the next 2 minutes. The owner answers such a refusal with `412 Precondition Failed`, naming both ids and logged at info (see the Logs upgrade note), and the dispatcher treats it as the retriable mismatch a local commit returns: the records, and what queued behind them for that partition, go back to the WAL and are checked again on the next rescan (discarded once the leader confirms their incarnation is gone, committed on their own partition once the owner's replica has caught up), without the owner being marked failing or the records being rerouted to a sibling partition. The single-record commit op carries the id and is checked the same way.
- A produce commit to another node carries at most 8 MiB of encoded records; the rest of the destination's queue follows in the next commit (see Fixed).
- The stage Grafana dashboard (`ops/monitoring`) counts batch produces (`/produce/batch`) and batch acks (`200`) with the single ones. Its produce and ack panels count requests, and a batch request carries up to 100 messages.
- The per-identity cap on concurrent consumes (`http.max_consume_in_flight_per_identity`) counts a batch consume as its `max`, clamped to the cap.
- A batch consume forwarded to another node hands the owner's reply (up to 8 MiB) to the client without copying it once more on the forwarding node. Nothing on the wire changes.
- The `hwm`, fan-out cursor and ingress WAL changes above, and the three new config file settings, have rollback conditions; see the upgrade notes below.
- The broker logs two warnings about the consumer offset committer, each at most once a minute. `consumer offset commits cannot keep to their interval: persisted offsets lag acks by about the flush time` (with `partitions`, `flush_took`, and the tick as `interval`) when one of its ticks takes longer than the tick (100 ms, or the durability interval when that is shorter), not counting a tick that took on partitions for the first time (after a start, most of them at once); the next tick then starts at once, and a process crash redelivers about a tick's duration of acks. `consumer offsets wait longer than their durability interval for a device flush: a power loss would redeliver more acks than it promises` (with `partitions`, `oldest` and `durability_interval`) when a partition's writes have waited more than twice `storage.consumer_offset_commit_interval_ms` to be synced. Fewer partitions per node or a faster disk helps with either.
- Log messages that a search or alert may match changed. The produce dispatcher's `rerouting produce records for dead partition owner` is now `rerouting produce records for unavailable partition owner`, and `rerouting produce records for stuck partition owner` gained an `err` field with the commit error. `drop topic schemas after retiring incarnation` is now `drop topic schemas after retiring or purging it`. A new warning, `discarding undispatched record of a deleted topic incarnation` (with `topic`, `topic_id`, `partition` and `seq`), is logged when the dispatcher, placing a `202`-acked record, destroys it because its topic was deleted and recreated under the same name while the record waited in the ingress WAL. One found that way only after a failed commit is logged as `discarding undispatched record for deleted topic`, as a deleted topic's records are (see [Discarding](docs/understand/produce-path.md#discarding-the-one-way-a-wal-record-dies-unfinished)).
- Opening a partition reads only its active segment (see Performance). A corrupt record in a sealed segment is found by the read that reaches it, where the open used to skip it in silence, and it is never served: consume skips it and counts it in `narad_consumer_corrupt_skipped_total` with a warning, replay answers `410`, fan-out counts it in `narad_fanout_child_dropped_messages`, all as before. An unreadable (`EIO`) sealed segment no longer fails the whole partition open; the reads that need it fail instead. See [Storage Engine](docs/understand/storage-engine.md#recovery).
- CI's race-detector step runs with an explicit 20-minute per-package timeout, and the unit-test job may run for 35 minutes (room for setup and the race builds above the per-package timeout), so a slow or hung package usually fails with Go's goroutine dump rather than a runner kill.
- `make test`, and so `make check`, passes the same 20-minute per-package timeout as CI, so `internal/cluster` no longer fails locally on Go's default 10 minutes when the machine is busy.
- `retention_ms: 0` on topic create and alter now means keep forever. Leaving the field out still gives the operator's default, and a negative value is `400`. Before, `0` meant the default on both, so a client could not ask for keep forever when the operator's default was an age (the Helm chart's is 12 hours). Clients that always send `retention_ms`, `0` included, for "use the default" must leave it out instead. See the upgrade notes for a leader still on 3.0.x.
- Schemas are stored compacted: `CreateTopic` and a schema change remove insignificant whitespace before checking and storing a schema, so the stored history no longer depends on the client's formatting. Versions stored before stay as they were; whether a schema is unchanged is still decided by JSON value.

### Deprecated
- `storage.high_watermark_sync_interval_ms` has no effect, since an open log no longer persists its high-watermark. The field is kept and any value passes validation, so code that sets it keeps loading. It was never settable from the config file or the environment.

### Performance
- A partition commit pays one fsync instead of two: the high-watermark file is no longer fsynced on every commit under the produce lock.
- Commit batches that queue on one partition while a commit runs share the next cycle's single write, fsync and read-back instead of paying one each.
- On macOS, WAL, segment and directory syncs issue `F_FULLFSYNC` through `x/sys` as a proper system call, so the Go scheduler releases the goroutine's P for the length of the sync and garbage collection no longer waits behind it. Durability is unchanged.
- The ingress WAL recycles two staging buffers across group commits instead of allocating one per batch, and its replay aliases payloads, interns topic names and pools its read buffers.
- The consumer offset committer runs at two cadences. Every tick (100 ms, or the durability interval when that is shorter) each partition whose acked state changed gets its `consumer.ahead` record, which carries the frontier and the out-of-order ack set, written into the page cache through a descriptor the committer keeps open, with no sync. Once per durability interval (`storage.consumer_offset_commit_interval_ms`, 1 s by default) each partition written since is written out once, the writeouts spread over the interval's ticks: `fdatasync` on Linux, and on macOS `fsync(2)` followed by one `F_FULLFSYNC` per device for the whole tick instead of one per partition. `consumer.ahead`'s two slots become a durable anchor that is never written while it is the anchor and a window the ticks overwrite, flipped by each successful writeout, and `consumer.offset` is brought level with the frontier at most every 30 s and at `Close`. The committer used to make every changed partition durable on every 100 ms tick, one device flush each: on macOS that flush took 67 ms at 12 changed partitions, 366 ms at 64 and 1.5 s at 256, so persisted offsets lagged acks by that much, and an owner's produce commits beside it ran at about half their rate. Measured on macOS against it: an owner's commits beside 64 dirty partitions went from 82.9 to 168.4 a second, eight spread produce streams beside 12 from 291 to 418 commits a second with p99 from 78.7 ms to 39.3 ms, and a tick that writes out every partition, as `Close` does, takes 5.8 ms, 9.3 ms and 21 ms at 12, 64 and 256 partitions; nothing was slower at any partition count, and the ack path is unchanged. It holds up to min(4096, a quarter of the soft open-file limit) descriptors open. See [Consume Path](docs/understand/consume-path.md#how-acks-reach-the-disk) and the upgrade notes below.
- Frames written while a partition has readers go into the frame cache as they are written, so a consumer at the tail reads them without a disk read or a decode. Frames decode without copying each record, a zstd frame read by a log whose codec is not zstd shares one decoder, frame encoders and read-back buffers come from shared pools instead of being pinned per partition, and the navigation cache stops at the first frame that covers an offset.
- Partition log lookups (`Logs.Get`) and the produce lock no longer allocate, and the pause checks cost one atomic load while nothing is paused. A consume scan resolves its first partition's log alone, so a hit there opens nothing else, and only after a miss resolves the rest of the topic's local partitions in one lookup (`Logs.GetMany`, up to 16): an empty consume costs 18% less over 8 local partitions, 22% less over 12 and 58% less under parallel load, and a hit costs what it did.
- Schema validation walks produce payloads with a pooled token decoder. After a schema change each node reads the topic's latest schema once and compiles it once, shared by every produce waiting on it; before, every waiting produce read the whole history and compiled it.
- The authentication middleware decodes the Basic credentials into a stack buffer on its cache hit path, and the consume encoder writes keys, topics and receipt handles with an allocation-free JSON string appender.
- Cluster RPC: frames over 256 KiB are written without a staging copy, replies are encoded into recycled buffers, request decoders stay on the stack, a forwarded reply without a body is written as a bare status, and forwarded acks, probes, claims, token calls and remote produce commits hand the transport a per-call budget instead of deriving a timeout context each.
- Consumers parked on one node share token registrations, and a parked consume no longer advances the owner probe cursor.
- Forwarded acks to one owner share RPCs under heavy load. While fewer than max(128, 8 x GOMAXPROCS) ack RPCs to an owner are in flight (twice the owner's messaging-handler bound), an ack goes out at once on its own, as before; past that, further acks queue and leave together as one `AckBatch` RPC (up to 64 records) the moment a slot frees. Each HTTP ack still gets exactly the response its own RPC would have, and the owner applies a batch under one handler slot. Measured against v3.0.1 with 1 to 512 acks in flight to one owner and round trips of 0, 200 µs and 1 ms, no point was slower; from 256 in flight, a half to a quarter as many RPCs go out. These batches, and a client batch ack's batch to each owner, are counted under a new `op="ack_batch"` on the cluster RPC metrics (see the Metrics upgrade note).
- The produce dispatcher wakes as soon as a record becomes durable instead of on its next 10 ms poll, so at light load a record no longer waits up to 10 ms (about 5 on average) for its commit to start.
- While other commits run, a produce destination holding fewer than 64 records waits for more, up to twice its owner's recent commit latency and at most 50 ms, so an ingress WAL group commit no longer turns into one small commit and one partition fsync per partition on the disk the next group commit waits for.
- The dispatch checkpoint's `fdatasync` is off the dispatch path: the value is written in place at once and flushed in the background within 250 ms, one flush for however many stores landed meanwhile. The trade is more duplicates after a power loss or kernel crash, where v3.0.1 synced the checkpoint on every store: the messages dispatched in about the last 250 ms can be committed again at new offsets and delivered twice. A process crash is unchanged. See the upgrade notes. The ingress WAL is compacted only behind a checkpoint value that is already on disk, so compaction trails a store by at most one flush.
- Fan-out commits a slab's child-partition batches concurrently (up to 16 at once), and reads parent slabs without copying the records.
- The lease tracker's expiry heap is typed (no interface boxing), its clock is read without a lock, and its shard table is a `sync.Map`.
- Opening a partition no longer reads or CRC-checks its sealed segments: a sealed segment's range ends at its successor's base offset, taken from the file names. On 256 MiB of 4 KiB frames an open went from about 94 ms and 287 MiB allocated to about 0.5 ms and 13 KiB (macOS, warm page cache), which speeds up restarts and the reopens after idle eviction, retention changes, move installs and the cold-retention walk. The active segment's walk streams its frames through one buffer, about 20% faster. Startup opens the owned partitions of up to min(8, GOMAXPROCS) topics at once: 93 partitions over 31 topics holding 1.2 GiB went from about 297 ms to 18 ms with both changes. A node's whole restart-to-ready time, dominated by its metastore catch-up, did not move measurably at 400 MiB per node.
- The fan-out and move reconcilers skip their once-a-second pass while the replica's topic, assignment, schema, user and routing-member versions have not moved, read through a new metastore accessor, `LatestDomainVersion` (member heartbeats and drain flags do not move them). A full pass still runs at least every 30 s, on every fan-out orphan-sweep tick, after a failed or unfinished pass, on the first tick after the replica catches up, and after any cursor or move worker exits. One tick of both, over 12-partition topics with no links or moves, takes about 91% less time at 100, 1,000 and 5,000 topics (29.5 ms to 2.8 ms at 5,000).
- Replacing a peer's consume token on the owner, and a consumer giving up its place in the owner's waiter queue, cost O(1) amortized instead of a scan and copy of the topic's queue: with 1,000 entries queued, a re-registration went from about 550 ns to 100 ns.
- The owner remembers each forwarded consume's delivery for 2 s so a cancel that races the reply can give the records back, and expiring those records costs O(1) amortized: every expiry used to shift the whole queue under its lock, about 60 µs per delivery at 50,000 deliveries a second in a benchmark, 141 ns now.
- A local consume writes the delivered record into its pooled buffer without boxing it for `WriteJSON`: 2 fewer allocations per delivery (the HTTP edge benchmark went from 721 ns and 10 allocations to 657 ns and 8).

### Security
- Node RPC (QUIC, UDP on the API port) on a node with security on now always requires a cluster secret. A secured node with no cluster peers and no `NARAD_CLUSTER_SECRET` generates a random secret for the life of the process (crypto/rand, kept in memory, never logged or written), so its node RPC answers only itself, and logs `single node with no cluster secret: generated a per-process secret, so node RPC is closed to other processes; set NARAD_CLUSTER_SECRET on every node before adding peers, and note that a node whose raft first started on a loopback cluster.addr can never take peers` at info. A node started with security disabled and no secret serves an open node RPC plane, as that mode opts into, and now logs a warning naming it (`node RPC plane is unauthenticated: ...`). The listener also refuses to serve a secured node that has no secret, whatever its peer count, and stops the node instead. Nodes with peers are unchanged.
- A node with security on and no cluster peers refuses to start with a plaintext Raft transport on a `cluster.addr` that is not a loopback address, as a node with peers already did: set the Raft TLS files, bind `cluster.addr` to a loopback address on a node that will never take peers, or set `security.allow_plaintext_raft` once the port is fenced. A loopback bind is for good: the address a node's Raft first starts on is recorded in the Raft configuration, the nodes that join later dial it, and a later `cluster.addr` does not change it, so a node first started on loopback cannot be grown by rebinding it. A loopback `cluster.addr` (the quickstart's `docker run`, `--dev`) still needs nothing. A node whose recorded Raft address is not the one it now advertises says so at startup, naming both addresses, at error level unless it is alone in the Raft configuration and advertises a loopback address. The startup warning about a plaintext Raft transport now names why the node runs one (security off, `security.allow_plaintext_raft`, or a loopback address); it used to name `security.allow_plaintext_raft` whatever the reason.
- A JSON request body with a second value after the first is refused after reading one token of that value. The whole trailing value used to be decoded, so a 1 MiB body of `{}` followed by a large array allocated about 70 MB, on every endpoint that decodes a JSON body, topic create included, and before that endpoint's authorization check.
- The Go toolchain is pinned to 1.27.1. The pin started at 1.26.6, which carried fixes for four standard-library advisories the new `govulncheck` job found on its first run against 1.26.0: quadratic complexity in `net/url` path resolution (GO-2026-6218), unbounded post-handshake messages in `crypto/tls` (GO-2026-6090), `ReadHeaderTimeout` not applied during the unencrypted HTTP/2 check in `net/http` (GO-2026-6089), and unbounded recursion in `encoding/asn1` (GO-2026-5972). A scan on 1.27.1 reports none of them, and no others.
- The Raft leader re-checks that the caller owns the topic or is an admin for every topic change (alter, schema, delete, attach, detach, create-as-child) and that a create matches the caller's create grant, under the topic's lock and against the topic as it stands, and a follower now forwards the caller with the write; the leader looks the caller up in its own replica (an unknown caller is `403`). A non-admin's change naming a topic that the receiving node's replica does not have is answered `404` once the node has caught up with the leader (`503` if it cannot reach it), instead of being forwarded as allowed, which let a racing user delete or attach to someone else's new topic.
- A produce to a topic with a schema is refused with `400` (`payload nests deeper than 256 levels`) when its payload nests deeper than 256 levels of objects and arrays, before validation. The decoder allowed 10,000, and a deeply nested invalid payload made the validator build an error at every level: one 20 KB payload against an ordinary recursive schema made a node hold about 800 MiB, 2.4 GiB for a JSON-value union. A rejected payload whose full report would pass 32 MiB is checked without one and gets a summary.
- Schema registration refuses a schema through which one value is checked against one subschema along more than 64 paths, including acyclic `$ref` chains and references through `$anchor`, `$dynamicAnchor`, `$id` and draft-04 `id` fragments, nested resources, pointers into members no keyword owns, and `$dynamicRef`. Such a schema made every produce take exponential time: 1.4 KB took 2 s to check `"x"`.
- An `enum` of 16 or more values is checked by hash, and registration refuses a pattern that can cost the matcher more than 32 steps per byte of the string, counting each partial match kept alive and each assertion, alternation or capture walked (an unanchored `a.{1000}b`, `(?:\B){1000}x`). A 45,000-value integer allowlist cost 14 s for 1000 items, and either pattern seconds per 1 MiB string.
- Costly validations run under a per-node bound of one per CPU core: payloads above 16 KiB, and any payload on a schema registered before these checks, listing more than 1,024 required names or 64 `patternProperties` keys, or applying more than 64 subschemas to one value (such as a `oneOf` or `anyOf` union of 64 or more branches). When the bound stays full for 5 s the produce gets `503` (`schema: validation capacity busy, retry`), nothing is stored, and it can be retried on another node.
- A topic's stored schema history is limited to 4 MiB and every schema in the cluster to 256 MiB, counting the copy each fan-out child keeps; a schema change, a create with a schema, or a create-as-child or attach adopting a parent's history past either gets `409` naming the budget. A change that only edits annotations (`title`, `description`, `examples`, `$comment`, `default`, `deprecated`, `readOnly`, `writeOnly`) registers nothing and answers `200` with the current version; twenty such edits used to append twenty full versions to the replicated history.

### Fixed
- A partition move whose ownership flip committed while the destination saw an error (leadership lost mid-commit, a lost forwarded reply) could lose the whole partition: the destination deleted the copy it had just installed, served the partition from an empty log, and the old owner's stale-copy sweep then deleted the only other copy. The destination now keeps the installed copy and asks the Raft leader (through a barrier) what happened. A committed flip is done. A flip that can still commit is proposed again under the source's freeze for at most 2 minutes. The copy is taken off the partition's path only once a leader read that started at least 15 s after any proposal whose outcome was unknown confirms the flip did not commit, and it is renamed back to staging. When the leader refused the flip (the move was re-planned or aborted, or the topic was deleted), the flip can never commit: the worker ends and removes that staging copy, keeping it only if this node owns the partition by then. When the flip only stopped being proposable (the source's freeze lapsed, its high watermark moved, or the 2-minute limit passed), the same worker resumes from the staged copy and drains the source again instead of wedging. A source that dies under an unconfirmed flip is force-promoted as before. A retried flip of a partition that already flipped is answered as done. A move that ends without a flip removes its staging copy.
- The old owner's stale-copy sweep deleted its copy without any check when the new owner reported no move marker (for example after the new owner came back on an empty volume), and trusted a marker whose copy had lost records. It now compares the new owner's segment listing with its own copy and quarantines its copy (renamed to `<partition>.quarantine` and logged at error level; Narad never serves it and removes it only with the topic) when the new owner holds no records, holds records without a move marker, holds a marker from a move off another node (the partition moved on again before the sweep ran, so the marker vouches for that node's records, not this copy's), or lacks or holds short a segment below the position it vouches for; it defers only while the owner cannot be asked. A destination's install whose flip never committed (the destination died with its flip unconfirmed and the target was cleared, or the move was re-planned while its flip was unconfirmed) is judged like any other copy: it is quarantined and logged at error level unless the owner vouches for it at its own marker's position.
- A partition moved back onto a node before that node's stale-copy sweep had judged its old copy (the rebalance pass runs every 10 s, the sweep every 30) had the old copy deleted by the move's install, whatever it held: records the node committed past a force-promote while it was cut off, or records the new owner had lost since. The install now quarantines any copy at the partition's path that holds unexpired records (renamed to `<partition>.quarantine` and logged at error level) and replaces only an empty one: no comparison with the incoming copy is trusted to prove the old one redundant. The sweep likewise never trusts an old copy's own move marker to relax its check, so an install that never flipped is quarantined, not reclaimed.
- A move's destination did not sync the copy it installed: the copied segments, the position files, the staging directory and the rename into the partition's path all sat in the page cache when the flip was proposed, and the old owner's sweep, which reads the new owner's listing (sizes from that same page cache), could delete the old copy up to 30 s later, inside the usual writeback window. A power loss on the new owner then lost records that existed nowhere else. The destination now fdatasyncs each sealed segment once its last chunk is staged (mostly during the pre-copy, so the freeze has little left to sync), every other staged file before it writes the move marker, the marker and the staging directory after it, and the topic directory and the topics root after the install's rename, all before the flip; the marker records it (`durable_at_unix_ms`). The old owner's sweep waits until an install is 5 minutes old before it trusts a new owner whose marker has no such stamp (an older destination).
- A node whose dispatch checkpoint came back from a crash more than the dispatcher's read-ahead below the oldest ingress WAL segment (a disk that lost the checkpoint's last write while the segment deletions survived) stopped dispatching for good: every later produce on it was answered `202` and never committed. The node now starts dispatch at the oldest segment, which is safe because segments are only deleted behind committed records, and logs `ingress dispatch checkpoint was below the oldest WAL segment`.
- Stale version references in the documentation. The README advertised v2.2.0 and the deployment page told people to run a v0.2.0 beta image, five releases after it was superseded.
- A link on the schemas page that pointed at an anchor on a different page, so it silently went nowhere.
- The signature verification recipe in the README pinned only the repository, so it would have accepted a signature from any workflow on any branch. It now pins the publishing workflow on `master` or a release tag, and CI verifies the exact identity it just signed with.
- `scripts/check-release-refs.sh` no longer passes a pinned pre-release. Its pattern had no right anchor, so `v1.2.0-rc.1` matched as far as `v1.2.0` and compared equal to the release, which is the one case the check exists to catch. It also checks every reference on a line rather than the first.
- The nightly heals leftover firewall rules before it starts. Its cleanup does not run on `SIGKILL`, so a cancelled run left `DROP` rules on the ports the next run uses, which then failed while pointing at the broker.
- The nightly's numeric options are validated before they reach shell arithmetic, and the workflow passes its dispatch input as a single argument. Neither an arithmetic payload nor a smuggled second option can reach the run.
- A message key containing a control byte, invalid UTF-8, or certain non-printable characters made the whole consume response invalid JSON, which could stall a consumer on that partition. Keys are now JSON-escaped, and a non-UTF-8 key is returned base64-encoded (see Changed).
- JSON error bodies built from a request path value with a control byte or invalid UTF-8 were invalid JSON.
- A produce with a large declared `Content-Length` allocated the whole declared size before the body arrived, so a slow or stalled upload could pin up to 1 MiB per request. Bodies over 64 KiB are now read into a buffer that grows as data arrives.
- Requests sharing one bcrypt verification all failed with `499` when the first of them disconnected.
- The ingress WAL fsyncs its active segment when it opens. Its open-time scan reads the file through the page cache, so after a process crash it counted frames the dead process wrote but never synced as synced and replayed them to the dispatcher. A power loss soon after the restart could then leave the dispatch checkpoint ahead of the WAL, and the node refused to start.
- A cancelled or timed-out caller could close a whole peer connection while a stream was being opened for it, failing every RPC in flight on it, and its cancellation armed the shared dial backoff.
- One late, expired or oversized request could abort a shared multiplexed cluster RPC stream and every request on it, frames over 256 KiB included.
- A dead or black-holed peer connection was only detected after QUIC's 30 s idle timeout when the timed-out callers carried their own deadline, which every hot-path caller does.
- A commit that passed the ownership and freeze check just before a rebalance handoff froze the partition could still append after the handoff read the final high-watermark.
- Records accepted before a topic was deleted and recreated under the same name could be committed into the new topic, by the node that accepted them or by the owner it sent them to.
- One slow, frozen or hung partition owner held up produce dispatch for every partition on the node, its own local ones included: each dispatch pass waited for every commit it started, up to 30 s for an owner that stopped answering. Any failed commit also put the whole dispatcher to sleep for a second, even when everything else in the pass had committed.
- Deleting a topic that had records waiting in the ingress WAL stalled dispatch on every partition while each record was confirmed deleted with its own leader round trip.
- A backlog of large records (about 4 KiB each or more) for one partition on another node could build a commit batch over the 16 MiB cluster frame limit, which failed the same way on every retry, so the partition never drained.
- The produce dispatcher's owner-lookup cache kept an entry for every topic ever deleted, so a workload that creates and deletes short-lived topics grew it without bound.
- Commit times could go backwards along a partition (a batch that lost the race for the produce lock, or a wall-clock step back), which held due records back at a fan-out delay gate.
- A retention change, partition reclaim or shutdown that overlapped a produce commit could make that batch visible twice.
- A move install racing a commit on the same partition could deadlock.
- Deleting a large topic, or opening a closed partition with a large backlog, stalled produce and consume of every other topic on the node for the length of the unlink or the recovery.
- The consumer frontier file could move backwards when two acks' frontier advances reached the offset committer in reverse order, so a restart, graceful or not, could redeliver acked messages.
- A consumer could wait out its whole `wait` although records were available: a wake arriving while the pump held a popped waiter was dropped when the topic's last other waiter left.
- A consume could answer `410` to a consumer that held no receipt handle when a concurrent consume skipped the same retention gap first.
- A consumer woken by a token notification it could not use (served locally, or out of budget, at that moment) took the wake with it, and the node's other parked consumers waited for the next registration refresh, up to 5 s.
- A consume kept probing further owners after its client had gone.
- A partition transfer's multi-megabyte chunks shared a connection with commit replies and could delay them.
- The lag, oldest-unconsumed-age and size series of a partition vanished once its log was idle-evicted, and a partition with no consumer state after a restart reported its whole log as lag.
- A deleted topic's storage and counter series were re-created while one of its logs stayed open.
- A schema-hydrate race could leave a node validating produces against an older schema until the next schema change.
- A schema registry drop under a live topic of the same name (a purge of a deleted incarnation) let later produces through unvalidated.
- Deleted topics left cached topic records, assignments, schema markers, consume cursors and queue state behind on every node that had served them, and a metastore version cell per name on every node.
- On a fresh or fully restarted cluster, a topic created right after `/readyz` could wait up to 10 s for owners, with produces parked and consumers answered `204` in a busy loop. Nodes now retry member registration every 250 ms until it first succeeds, and the leader assigns and rebalances within about a second of a member turning alive.
- A topic create and the controller's assignment sweep could overwrite each other's partition owners.
- While a fan-out child partition's owner was down, every retry re-sent the whole slab, duplicating it into the healthy child partitions each cycle.
- A force-promoted partition could start with its consumer frontier past its own log end, so records the new owner committed there were readable but never delivered. The source's transfer listing read the high-watermark before the consumer frontier, and a record committed, delivered and acked between the two reads put the frontier at or above it; a move whose source then stayed dead past `ForcePromoteAfter` promoted that listing. The listing now reads the frontier first; both sides clamp the committed offset to HWM-1 and the acked-ahead set below the HWM, and the destination lowers fan-out cursors to the HWM. A raced listing now costs redelivery of the records acked in that window. Present from v2.0.0 through v3.0.1.
- A partition moving back onto a node that still held consumer state from its earlier ownership could get that state's frontier written into the copy the move installed, and the new owner then skipped the records between the copy's frontier and the old one. The offset committer wrote an ack's commit by path into whatever directory held the partition, even once the state behind it was dropped, and the move dropped that state only after the install, so an ack landing in between still had it. The committer now writes nothing for a partition with no live consumer state, and the move drops that state before the install as well as after it. Present from v2.2.0 through v3.0.1 (before v2.2.0 a move never dropped that state).
- A topic deleted and recreated under the same name could skip its first records on a node that had served the deleted topic, because the deleted topic's consumer frontier reached the new topic's partition. The deleted topic's consumer state was dropped only after the new partition directory existed, so an ack landing in between wrote its frontier there; a consumer rebuilding that state from the old files while the drop ran could keep it alive past the drop; and a consume still holding the deleted topic's closed log read the reserved offset there as "not found" and skipped the new topic's frontier to the old log's retention floor. The state is now dropped right after the old directory is renamed away, before the new one exists; a drop waits for a rebuild that already read the old files; and a closed log answers every read with `ErrLogClosed`, which the consume path treats as a transient error, never as a gap to skip. Present from v2.2.0 through v3.0.1.
- A topic purge that raced a consumer offset write could fail with `directory not empty` after removing the directory's marker, and a same-named topic created afterwards adopted the leftover, with the deleted topic's consumer frontier, and skipped its first records. The purge now renames the topic directory aside before it removes it, and drops the topic's consumer state before the removal as well as after. Present from v2.2.0 through v3.0.1.
- A move whose flip was rejected, or a reclaim of a partition that moved away, could remove a recreated topic's partition directory, with its records and consumer state, on a node already serving the new topic under the same name. The rollback and the reclaim acted on the partition's path without the topic's guard and without checking whose directory it named by then (a flip is rejected exactly when the topic was deleted under the move). Both now run under the topic's guard with the partition's log closed, as the install's swap already did, and all three act only while the topic directory still belongs to the incarnation they read; a copy left behind that way is quarantined with its incarnation's directory and reclaimed by the sweep. Present from v2.2.0 through v3.0.1.
- A newly elected leader applies everything the previous leader committed before it changes a topic (one Raft barrier per leadership term, before the first topic read-modify-write), so an alter served right after a leader change can no longer shrink the partition count or undo the previous write. A barrier that fails is a `503` to retry. A `PATCH` that sets one of the two per-partition caps also leaves the other to the leader, which keeps the value the topic holds under its lock; the node serving the `PATCH` used to carry it forward from a read of its own, which after a leader change, or beside a concurrent `PATCH` of the other cap, wrote an old value back over a committed one while both clients got `200`. A 3.0.x leader still does that until it is upgraded.
- The controller's placement pass waits for the leader to apply the log, re-reads each topic under the assignment lock and skips one deleted or recreated in the meantime, and a topic delete holds that lock, so the pass no longer writes owners for a deleted topic (which a later same-named topic inherited) or replaces an owner the previous leader placed.
- New partitions (a create, a partition increase, the controller's sweep) are never placed on a node being decommissioned. While every live node is draining (say two draining nodes while the others restart), a create or partition increase is refused with `503` before anything is written (`every live member is being decommissioned, so no member can take new partitions; wait for restarting members to come back, abort a decommission or add a node`), the controller's sweep leaves unowned partitions unowned until a node that is not draining is alive, and the leader logs `every live member is being decommissioned, so new partitions have no owner ...` at error level, once per episode.
- A topic whose name differs from an existing one only in letter case is refused with `409` naming the existing topic; on a case-insensitive filesystem (APFS, NTFS, Docker Desktop bind mounts) the two shared a directory and one lost its data. Existing pairs keep working.
- New topic names are limited to 200 bytes, so the file names derived from them (quarantine directories, fan-out cursors) fit the filesystem's 255-byte limit; a longer name is `400`. Existing longer names keep working, but one over 230 bytes cannot become a fan-out child, since the name of its fan-out cursor file would pass the limit and fan-out to it could never start.
- A topic delete no longer leaves the deleted topic's files on other members when the client disconnects or times out: the purge fan-out runs detached from the request under its own time budget (about 17 s) and names the incarnation the delete removed, read under the topic's lock, where it used to name the one read before the delete, which an interleaved delete and recreate made the wrong one. A member whose replica has not yet applied the delete answers that it will purge later (`503` with code `purge_deferred`, logged at warning level as `purge deferred: ...`) instead of a `204` that hid the skipped purge, and is retried, as is an unreachable member, up to three attempts; members still owing a purge are logged once at error level, `topic purge unfinished on some members; ...`, with the topic, the incarnation and the member IDs, and their copies stay until their startup orphan sweep.
- Every topic create, alter, schema change, delete, attach and detach now writes an audit line (`component=audit`, with actor, target, outcome and status) on the node the client called, including changes forwarded to the leader. A forward that ended without the leader's answer, a `503` from a leader that lost its leadership while committing the change, and a client that went away mid-change are recorded as `outcome=unknown`, never as rejected or failed, since the change may have been applied. A `PATCH` that fails part way logs the fields it applied before the failure as `ok` (as `unknown` on a node that forwarded it, which cannot tell how far the leader got), so a retention cut sent with a schema the leader refuses is not logged as rejected. See [Read the audit log](docs/operate/monitoring.md#audit-log).
- `GET /v1/topics/{topic}` and `narad server report` answer with the live partitions when a partition owner is down, instead of `421` (or `500` while the owner was still unreachable). Each partition carries `status` (`ok` or `owner_unavailable`) and, when unavailable, `owner_liveness` (`dead`, `unreachable` after 2 s without an answer, `unknown` or `unassigned`); the body carries `partial: true`. Assignment rows beyond the partition count no longer add entries, and a failure to read the node's own metadata is `503`. The report marks such a topic `[k of n partitions unavailable]` and leaves unavailable partitions out of its totals and owner count, and `narad replay` and `narad sub --peek` refuse an unavailable partition instead of starting from offset 0.
- Describing a topic reads only its latest schema version, and the per-partition stats each owner serves read none, so a dashboard polling a topic with a long schema history no longer reads and copies the whole history per partition; reading the latest version itself now costs the same for 60 versions as for one (189 allocations before, 12 after).
- A node whose metastore meets a Raft entry type it does not know stops applying entries, leaves Raft and exits non-zero, logging `metastore: stopped applying raft entries` with the entry's index, its type, this build and that a newer release proposed it. It used to skip the entry and keep serving a diverged copy of the cluster metadata. A restart replays the entry and stops again until the node runs the cluster's release.
- A metastore write that fails on the node's disk (a full volume, an I/O error) is retried for up to 30 s (`metastore: could not write raft entry; retrying`, warning) and then stops the node the same way; the entry is applied once the disk is fixed and the node restarts. It used to count as applied, so that node silently lacked the change while it reported ready. A refused write (a topic that already exists, a compare-and-set miss) is still answered and counted as applied, as on every other node.
- A restart no longer applies Raft entries a second time on top of the metadata database. Each entry's index is stored with its effects and the replay skips what the database already holds, so an entry that was refused (an attach, say) can no longer succeed on one node's replay. A restart after a Raft snapshot no longer restores the snapshot over a database that is already newer, so the replay after a restart takes milliseconds instead of one synced write per entry.
- After a restart from a Raft snapshot in a quiet cluster a node reports ready without waiting for a new metadata write.
- Raft snapshots of the metadata database no longer hold it in memory. A snapshot is copied to a temporary file beside `fsm.db` under a short read and streamed to Raft from there, and a restore is streamed to disk. A snapshot used to copy the whole database into memory and a restore to read the whole image (a 26 MiB `fsm.db` allocated 64 MiB per snapshot and 54 MiB per restore; both now allocate under 100 KiB), so a large enough metastore could crash every node at its next snapshot, and again when it restored one. A snapshot now needs free disk equal to `fsm.db`'s size for the copy; without it the snapshot fails with `metastore: could not copy the database for a raft snapshot` (error) and `narad_metastore_snapshot_failures_total`, and Raft tries again at its next interval. See [Snapshots](docs/understand/metastore-and-raft.md#snapshots).
- A node joining the cluster is admitted as a Raft non-voter: it replicates but does not count toward quorum until it has caught up and asks again, and the leader promotes it to voter once it has led for 12 s and sees the joiner answering heartbeats with an alive, non-draining member record. Admitting a joiner that could not be reached while another voter was down used to leave the cluster without a leader, with no way to remove the new voter. A non-voter is never removed or promoted on its own; `narad_raft_nonvoters` shows any that stay, and the joining node logs the leader's reason for deferring its promotion at info (`cluster join: caught up as a raft non-voter; the leader defers promotion`). A join's `200` body carries `status` (`staged`, `deferred`, `promoted` or `voter`) and `reason`. See [Cluster lifecycle](docs/understand/cluster-lifecycle.md#join-promotion).
- A join or readmission reaches the leader when it is not one of the pinned peers: a non-leader's `421` names the leader's ID and node-RPC address, and the joiner asks it next (at most 4 hints per attempt, up to 8 learned leader addresses kept for later attempts). After the leader moved to a node outside the pinned list, a scale-out used to retry `421` until leadership happened to move back.
- Decommission removes a drained non-voter from the Raft configuration too, without the MinVoters floor or the leader hand-off, which only voters need.
- Once every member runs this release, a topic create is one metadata write: the record, its first schema version and its fan-out parent link commit together. A leader change during a create can no longer leave a topic without the schema it was created with, or a child that copies nothing, and the `409` a retried create gets means the topic exists as requested. A placement pass during a create-as-child can no longer put the child's partitions on the parent's nodes.
- Topic alters, schema changes, deletes, attaches and detaches apply only to the topic incarnation the leader checked them against, and an alter never shrinks the partition count or changes the owner, creation time or visibility timeout. A request whose topic changes under it (deleted and recreated, or grown) is read and checked again once; if it changes again, the answer is `409` (`topic changed since it was read`).
- Re-attaching a child compares the two schema histories as JSON values, so a child whose history was copied from an API read (formatted differently from the parent's stored one) can be linked again.
- Partition placement is insert-only: the metastore refuses an owner for a deleted topic, an out-of-range partition or a removed member, and never replaces an owner on record. Assignment rows that earlier releases left for deleted topics, or past a topic's partition count, are pruned by the leader (when it takes over and about every minute), and a topic created under a name starts with none of the old rows.
- A dead mark carries the heartbeat it was decided from, so a heartbeat that committed after the decision wins, and a leader reading a lagging replica no longer marks a live member dead.
- The metadata state machine applies the schema byte budgets and the letter-case name check again for these writes, so two writes that both passed the leader's checks cannot together take a history past its budget or create two names that share a directory.

### Upgrade and rollback notes
- **Raft TLS on secured single nodes.** A node with security on, no `cluster.peers`, no Raft TLS files and no `security.allow_plaintext_raft`, whose `cluster.addr` is not a loopback address (such as `10.0.0.5:7943`, or `:7943` with `cluster.advertise_addr` set), now refuses to start with `security is enabled and the raft transport has no TLS, but cluster.addr ... is not a loopback address`. Before upgrading such a node, set the Raft TLS files on every node of the cluster ([Raft TLS certificates](docs/operate/raft-tls.md)), bind `NARAD_CLUSTER_ADDR` to `127.0.0.1:7943` only on a node that will never take peers (the Raft configuration keeps the address a node's Raft first starts on, and a later `cluster.addr` does not change it, so a node first started on loopback cannot be grown by rebinding it), or set `NARAD_SECURITY_ALLOW_PLAINTEXT_RAFT=true` once 7943/tcp is fenced. A node with no peers configured that other nodes have joined (they list it in their peers) is cut off from their Raft for good by a loopback bind or by Raft TLS on it alone, because such a node never runs the join loop: for it, `allow_plaintext_raft` (or Raft TLS on every node) is the only safe choice. A loopback `cluster.addr`, a node with security off, and Helm installs (which set peers and, by default, `allowPlaintextRaft`) are unaffected. A rollback needs no step.
- **Node RPC authentication on single nodes.** Nothing to do. A node with security on and no peers now closes its node RPC plane to other processes; it starts as before and logs the info line once. To add peers to such a node later, set the same `NARAD_CLUSTER_SECRET` on it and restart it before the first node joins; it also needs a `cluster.addr` the other nodes can reach, and either the Raft TLS files on every node or `security.allow_plaintext_raft`, or it is cut off from their Raft (see the note above). A node whose Raft first started on a loopback `cluster.addr` cannot be grown this way: the Raft configuration keeps that address, so the nodes that join cannot reach its Raft once it is not the leader. Start a new cluster whose first node starts on an address the others can reach, and move the workload to it. (A node with peers already had to have a secret; a joiner cannot authenticate to a node that has a per-process secret: its node RPC fails with `cluster rpc: read server auth proof: ...`, and the single node logs `cluster stream rejected: invalid auth`). The secret is not persisted, so a rollback needs no step: an older binary serves the plane as it did. Helm installs always set peers and, with security on, the secret, so they are unaffected.
- **Partition moves in a mixed-version cluster.** `CompleteMove` now answers `409` for a refused flip and `404` for a partition with no assignment (was `503`), and `GetAssignment` is answered only by the Raft leader (`421` from a follower) and marks its answer `leader_read`. Against an older leader an upgraded destination can confirm a flip but never undo one, so a move whose flip fails waits with its copy installed until the leader runs this release (or the move is re-planned). Against an upgraded leader an older destination behaves as before, and the leader answers its retried flips as done. An older node's sweep that asks a follower gets `421` and defers. An upgraded old owner reclaims its copy of a partition an older destination installed only once the install is 5 minutes old, because an older destination does not sync its copy before the flip; the move marker's new `durable_at_unix_ms` field is ignored by older readers. No data is at risk either way, and nothing new is replicated.
- **New log lines worth a search or an alert.** The two node RPC lines above. `move: flip not confirmed; resolving its outcome with the leader before undoing anything` (warning) and `move: the leader confirms the flip did not and cannot happen; moving the installed copy back to staging` (warning) from a move's destination. `move: set aside the staging copy of a partition this node owns; the partition's records may not all be under its path. Operator action required` (error), and its sibling for a move that took its install back and cannot read the owner: some of the partition's records may be only in the set-aside copy, `dataDir/.moves/<topic>-<partition>.quarantine`, which no later move clears (see [Troubleshooting](docs/operate/troubleshooting.md#log-move-keeping-staging)). `reclaim: the new owner cannot vouch for the local partition copy; quarantined instead of deleted, its records may exist only here` (error), with the sweep's `move: stale partition copy QUARANTINED, not deleted: the new owner cannot vouch for it; operator action required`. `move: the partition's path held an earlier copy with unexpired records; quarantined instead of replaced, since it may hold records the incoming copy lacks. Operator action required` (error), from a move's install. `raft configuration records this node at an address other than the one it advertises` (error, at startup, with `recorded_addr` and `advertise_addr`): the other nodes dial the recorded address, and a later `cluster.addr` does not change it (see [Troubleshooting](docs/operate/troubleshooting.md#log-raft-address-recorded)).
- **Ingress WAL record format 2.** Every accepted produce for a topic with an incarnation id (any topic created on v2.2.0 or later) is now written in record format 2, which carries that id; records for an older topic stay in format 1. This release reads format 1, so the upgrade needs nothing, and a mixed-version cluster is fine (see the mixed-version note below). v3.0.1 and earlier cannot decode format 2: a node rolled back with an undispatched format-2 record stops dispatching at it, keeps answering produce with `202`, and delivers nothing it accepted from then on until it runs a newer binary again. Nothing is lost. Before rolling a node back, drain its ingress WAL: pause producers, keep every partition owner up, and wait until `narad_ingress_dispatch_backlog_records` is 0 on every node (in a sample taken after the pause; the gauge is refreshed every 5 s). A node stops dispatching as soon as it receives `SIGTERM`, so a plain rolling rollback under produce load can leave a few such records behind. See [Rolling back to an earlier release](docs/reference/helm-values.md#rolling-back-to-an-earlier-release).
- **The `hwm` file.** After a clean stop it holds the exact boundary, as before, so a rollback after a clean stop is exact. After a crash it can be empty (the first commit after an open empties it). Every earlier release reads an empty file as "take the record tail" when it opens the partition's log, so an open log hides no acked record. Its readers of a closed partition read the same empty file as a boundary of 0, though, and an older binary rewrites the file only at its first commit on that partition. On v3.0.1 and earlier the transfer listing is one of those readers: for a partition the rolled-back node has not committed to since the rollback and has closed (idle eviction), it ships a boundary of 0. A force-promote off that node (a move whose source dies after a catch-up listing and before the freeze, and stays dead past `ForcePromoteAfter`) then installs a copy that hides every record until the new owner's next commit, and then redelivers the whole partition. At that boundary the promotion also accepts a copy of any length, so it can promote a partial copy; the returning source quarantines its own copy instead of deleting it, so those records can be recovered by hand. If the new owner's first commit fails, its discard truncates the copied active segment. Live moves and decommissions are not affected: their freeze opens the log, so they ship the boundary it takes from the tail. An older binary also exposes that tail without fsyncing it first, and the tail can hold frames the crashed process wrote but never synced (this release fsyncs the tail before it exposes it). A power loss before the older binary's first commit on the partition (or before the kernel writes those pages back) can then take back records it already served, and once their acks are persisted their offsets are reused, so the records committed there later can be skipped. So after any unclean stop (a crash, or a pod killed at the end of its grace period), starting the node once on this release and stopping it cleanly is a required step before rolling it back: startup opens every owned partition, and a clean stop writes each one's exact boundary. Give pods a `terminationGracePeriodSeconds` long enough to stop cleanly during the rollback itself: after the HTTP drain (up to `http.shutdown_grace`, 10 s by default), a clean stop syncs the consumer offsets of every partition acked since their last sync, then writes and syncs the `hwm` file of every partition written to since it was opened, one partition after another. Measured on local disk under Linux (in a container), that is about 0.1 to 0.4 ms and 0.6 to 1.6 ms per partition, so the chart's default 30 s covers roughly 10,000 such partitions; a network volume syncs slower, so measure on yours before relying on it. On this release, until a crashed partition's log is opened and closed again, readers of the closed partition (topic describe stats, the consume pump's backlog estimate, fan-out reads of a closed parent) find no boundary on disk, and the transfer listing opens the log to get one. Startup opens every owned partition before the node reports ready, so this is not normally visible.
- **Fan-out cursor files.** `fanout-<child>.offset` has a new fixed-size, CRC-checked format. Older binaries parse it (they ignore the `crc` field and the padding); an older binary that advances a cursor rewrites it in the old format, and this release reads and migrates that again.
- **Ingress WAL segment preparation** (`storage.ingress_wal_prealloc`) is opt-in and off by default. With it on, the WAL keeps up to two extra 64 MiB segments (the prepared active segment and a ready spare, `next-segment.prep`), and crash recovery changes: a group commit torn inside a prepared segment, including a hole of zeros followed by valid frames of the same write, is truncated at the first bad frame instead of failing the open, but only in the last segment, only in a segment that ends in the preparation trailer, and only within 16 MiB of the bad frame (larger group commits are written and synced in runs of at most 16 MiB). Within that window, damage to frames that were already synced is truncated too. A cleanly stopped prepared WAL opens on v3.0.1 and earlier without losing records, but a crash that tore a write inside a prepared segment, leaving valid frames behind a hole, can make those binaries refuse to start (a `corrupt frame` error). Turning the setting off on this release needs nothing: the next start trims the prepared segment and removes the spare. That is the way to roll back a node that ran with it on: remove the key from the config file (older binaries reject it, `true` or `false`; see Configuration below), restart the node once on this release, and then roll it back. The WAL it then holds grows by appending, as older binaries expect, so they open it even if the stop before the rollback is not clean. A clean stop with the setting on removes the spare too, but a node rolled back straight after an unclean stop keeps `<data_dir>/ingress/produce/next-segment.prep` (64 MiB) for good: older binaries never list or remove it. It is safe to delete once the older binary is running.
- **Mixed-version clusters.** A produce commit to another node now carries topic incarnation ids, and a forwarded ack may travel in the new `AckBatch` op. An owner on an older release refuses both with a `400`: the sender resends the commit batch without the ids and the acks one at a time, and keeps doing so for that owner for 2 minutes, so a rolling upgrade costs each sending node one refused commit batch and one refused ack batch per old owner every 2 minutes, and neither reaches a client as an error. Records committed to an old owner that way are committed by name, as before this release. A batch consume forwarded to another node carries its count as another trailing field of the `Consume` op (`Max`, after `Claim`); an older owner refuses it with `400`, is asked again for one record (a claim drops `Max` and then `Claim`, within its one 500 ms budget), and is remembered for 2 minutes, so a batch through an older owner carries one message. An owner of this release answers a produce commit whose records carry another incarnation's id with `412`; no earlier release sends those ids, so a mixed pair never sees it.
- **Batch produce, batch consume and batch ack** need the node that serves them to run this release. An older node answers a batch produce `404`, ignores `max` and answers a single message in the single-message shape, and answers a batch ack `400` (`receipt_handle required`), so move clients to the batch forms once every node they can reach is upgraded, or have them fall back to single produces on a `404`. A rollback is the same in reverse: before any node they can reach runs an older binary, move clients off all three batch forms, or make sure they fall back to the single forms on those answers.
- **Configuration.** New file settings `storage.consumer_offset_commit_interval_ms` (default 1000; see Consumer offsets below), `storage.ingress_wal_prealloc` (default `false`) and `http.max_produce_in_flight_per_identity` (default 0, off). v3.0.1 and earlier reject all three keys: a node rolled back with any of them in its config file (the chart's `narad.config`) fails to start, with `storage.<key> is an internal setting and cannot be configured` for a storage key and `json: unknown field "max_produce_in_flight_per_identity"` for the http one. Before rolling back to v3.0.1 or earlier, remove `storage.consumer_offset_commit_interval_ms`, `storage.ingress_wal_prealloc` and `http.max_produce_in_flight_per_identity` from the config file, even where they hold their default values. The env var `NARAD_HTTP_MAX_PRODUCE_IN_FLIGHT_PER_IDENTITY` can stay: older binaries ignore env vars they do not know. The failed start happens at config load, before any storage is opened, so removing the key is all a stuck pod needs. `storage.high_watermark_sync_interval_ms` is deprecated and ignored.
- **Consumer offsets.** `consumer.offset` and `consumer.ahead` keep v3.0.1's formats, so neither the upgrade nor a rollback needs a step for them: v3.0.x recovers the larger frontier of the two files, as this release does. What changes is when they reach the disk. The durability interval defaults to 1 s, where v3.0.1 synced every changed partition every 100 ms (its storage flush interval), so after a power loss, a kernel crash or an instance loss consumers can see up to about 1.1 s of acked messages again, where v3.0.1 redelivered about 0.1 s plus the time its sync took; a process crash still redelivers about 100 ms and a graceful stop none. All of them are duplicates, never loss. To keep the old window, set `storage.consumer_offset_commit_interval_ms` to 100 in the config file (and remove it again before rolling back; see Configuration). While a node runs, `consumer.offset` is brought level with the frontier at most every 30 s, so a tool that reads it alone sees a frontier up to about 30 s plus the interval old: read `consumer.ahead` too and take the larger. A release before v3.0.0 reads `consumer.offset` alone, so a rollback that far after a crash redelivers that much more; after a clean stop both files are exact. `consumer.ahead` (8 KiB) now exists for every partition acked since the upgrade, in-order acks included: the first tick after the upgrade creates one for every partition acked in order (about 0.55 s at 256 partitions on macOS), and each node keeps up to min(4096, a quarter of the soft open-file limit) of them open.
- **Produced messages after a power loss.** The dispatch checkpoint is written in place at once and synced within 250 ms, where v3.0.1 synced it on every store. So after a power loss, a kernel crash or an instance loss, the messages a node dispatched in about the last 250 ms (plus the time a sync takes) can be committed again at new offsets, and consumers get them twice. A process crash replays no more than before, since the page cache keeps the stored value. These are duplicates, never loss, and no setting brings back the per-store sync.
- **Metrics.** New gauges `narad_ingress_wal_failed` (alert on 1) and `narad_ingress_dispatch_backlog_records` (wait for 0 on every node before a rollback). The metastore and Raft series listed under Added are new as well (alerts in [Monitor and alert](docs/operate/monitoring.md#metastore-alerts)); a node on v3.0.1 exports none of them, so during a rolling upgrade only the upgraded nodes report them. `narad_storage_high_watermark_persist_duration_seconds` no longer has one observation per commit, only at most one per log open and one per close. The per-partition gauges now include owned partitions whose log is closed, so series that used to disappear on idle eviction stay, and `narad_partitions_total` and `narad_topic_bytes` count those partitions too: expect both to step up after the upgrade on a node with idle partitions. `narad_consumer_dropped_messages` is exported for closed partitions as well and no longer reports a partition's whole prefix below its log start as dropped when its consumer state is not loaded. `narad_cluster_rpc_requests_total` and `narad_cluster_rpc_request_seconds` gain the `op="ack_batch"` label value: one RPC carrying several forwarded acks, extends and nacks for one owner (a coalesced batch of up to 64 records, or a client batch ack's handles for that owner, up to 100). The series count RPCs, not records, so under load and for batch acks `op="ack"`, `op="extend_ack"` and `op="nack"` no longer count every forwarded ack, extend or nack: a panel that reads `op="ack"` as the forwarded-ack rate undercounts, and latency panels on those ops miss the batched ones. Add `op="ack_batch"` to them. An older node never sends the op, so it reports no such series. Batch produce adds a `route` value, `POST /v1/topics/{topic}/produce/batch`, to `narad_http_requests_total`, `narad_http_request_duration_seconds`, `narad_http_request_bytes_in_total` and `narad_http_response_bytes_out_total`. Batch consume and batch ack keep the single-message routes, and a batch ack is answered `200` whatever its handles' outcomes, where a single ack is answered `204`. Once clients batch, one request carries up to 100 messages, so request rates no longer track message rates: read `narad_messages_produced_total` and `narad_messages_consumed_total` for those. A panel that selects produces with `route=~".*/produce"` misses the batch route, and one that counts acks as `status="204"` on the ack route misses batch acks. The repository's stage dashboard (`ops/monitoring/grafana/dashboards/narad-stage-dashboard.json`) already counts both, as requests. The node dashboard's Storage Latency panel still plots `narad_storage_high_watermark_persist_duration_seconds` beside the flush, fsync and retention-run latencies, and that series no longer measures a commit.
- **Logs.** Besides the messages listed under Changed, these are new and worth a search or an alert. `move: source frontier reached past the copy's high watermark; clamped (the new owner redelivers those acked records)` (warning, with `topic`, `partition`, `source`, `hwm`, `committed`, `clamped_to` and `acked_ahead_dropped`) comes from a move's destination when the source's listing carried a consumer frontier past the copy's high watermark (see Fixed): the new owner will deliver acked messages again. `owner refused produce records accepted for another topic incarnation; checking them again` (warning, with `topic`, `partition`, `owner`, `records` and `err`) comes from the dispatcher when an owner answers a commit with `412`, and can repeat on every rescan until the owner's replica has caught up with a delete and recreate or the leader confirms the records' incarnation is gone. The owner logs its side at info as `commit produce batch refused: records accepted for another topic incarnation` (`commit produce refused: ...` for the single-record op), with `err`. `purge: set topic directory aside; removing it in place` (warning, with `topic`, `purged_incarnation` and `err`) means a purge could not rename the topic directory aside and removed it where it was, as earlier releases did. `consumer offsets: partition directory removed or replaced under its persisted state; its acks are not persisted until the partition is dropped` (warning, with `topic` and `partition`) means the offset committer found a partition's directory gone or replaced under the consumer state it was persisting (a move's install or a delete racing a commit tick), and it writes nothing for that partition until its consumer state is dropped, which the move or delete then does. `release a record left out of a batch consume` (warning, with `topic` and `err`) means a record a batch consume reserved but left out of its response could not be given back, so it is redelivered when its lease lapses instead of at once. `produce dispatcher: final checkpoint` (error, with `err`) comes at shutdown, when the dispatcher could not store its last checkpoint or compact the WAL behind it: the next start can replay records it had already committed, as duplicates, and on a node rolled back to v3.0.1 or earlier any format-2 record among them stops its dispatch (see Ingress WAL record format 2 above). `discarding undispatched record for deleted topic` now also carries `topic_id` when it is logged after a failed commit.
- **Partition segments.** Opening a partition now reads only its active segment, but the segment files are written as before, so either binary opens what the other wrote (checked by restarting one node of a 3-node cluster 14 times, alternating between a binary from before the change and this one, with high-watermarks and replay across every sealed boundary intact).
- **Go memory limit.** A node rolled back no longer derives the Go memory limit from its cgroup limit. If your pods rely on it, set `GOMEMLIMIT` explicitly (in the chart's `extraEnv`) before rolling back.
- **Message keys.** Keyless produces no longer get synthetic `key-<n>` keys, so consumers that read one see no `key` field instead; messages stored before the upgrade keep theirs. A key that is not valid UTF-8 now comes back base64-encoded with `"key_encoding": "base64"`; a client that ignores that field sees the base64 text as the key (before this release such a message made the response unparseable). Both depend on the node that handles the message, so until every node is upgraded: a keyless produce accepted by a node on an older release still gets an invented `key-<n>`, and a consume served by a partition owner on an older release still returns the old key encoding (no `key_encoding`, and a key with a control byte or invalid UTF-8 can still make the response invalid JSON), including when an upgraded node forwards the consume, since it passes the owner's reply through unchanged. On a replica child (a fan-out child created with `parent`), fan-out runs on the node that owns the parent partition, and a node on an older release places a message with no stored key round-robin in the child, independently of its parent partition. So while such a node still owns parent partitions, a keyless message that an upgraded node accepted (and so stored without a key) and that the older node fans out can get both copies on one node; nothing moves those copies later. A message an older node accepted carries its invented key and keeps its copies apart on either release. A rollback has the same gap: a keyless message this release stored without a key, fanned out after the rollback, can get both copies on one node.
- **Topic changes during a rolling upgrade.** A follower on this release forwards the caller with a topic create, alter, delete, attach or detach. A 3.0.x leader refuses that field before acting on the request; the follower then resends the request once without it and logs `the leader predates forwarded callers ...` at warn (at most once a minute per leader), so the write still lands, checked for ownership on the follower only, as before the upgrade. A change forwarded by a 3.0.x follower carries no caller and is checked on that follower only until it is upgraded. Nothing in the Raft log changes, so replicas on either release agree and a rollback needs no step.
- **Keep-forever retention during a rolling upgrade.** An upgraded node sends an explicit `retention_ms: 0` to the leader as `-1`, which a 3.0.x leader refuses with `400`; retry once the leader is upgraded. A 3.0.x follower forwards `retention_ms: 0` both for an absent field and for an explicit `0`, and an upgraded leader reads that `0` as the operator default, which is what it meant on 3.0.x. A topic stored with keep forever (`retention_ms` 0) reads the same on either release.
- **New refusals clients can see.** `404` instead of a forward for a non-admin change naming a topic the receiving node does not have after it caught up with the leader (`503` when it cannot reach the leader); `403` from the leader in a race with a delete and recreate; `409` for a name that differs from an existing one only in letter case; `400` for a new name over 200 bytes; `503` for a create or partition increase while every live node is being decommissioned. A refusal the leader answers with `503` reaches a client that called a follower as `503` with the leader's message, where it used to be `500` (`create topic failed`).
- **Topic purges during a rolling upgrade.** An upgraded member whose replica has not applied a delete answers the leader's purge with `503` (code `purge_deferred`) instead of v3.0.1's `204`. A v3.0.1 leader treats it as a failed member and logs its usual warning; the member's startup orphan sweep reclaims the files, as for any missed purge. An upgraded leader treats a v3.0.1 member's `204` as done, as before. Nothing in the Raft log changes; a rollback needs no step.
- **Partial topic details.** Only an upgraded node answers `GET /v1/topics/{topic}` partially; a v3.0.1 node still answers `421` while an owner is down. The new fields (`partial`, `status`, `owner_liveness`) are additive and absent from an owner's per-partition stats reply, so either release decodes the other's. Tools that sum `partition_stats` must skip entries whose `status` is `owner_unavailable`: their zeros are placeholders.
- **New log lines worth a search.** `topic purge unfinished on some members` (error, on the leader) and `purge deferred: the local metastore still shows the topic incarnation` (warning, on the member); see [Troubleshooting](docs/operate/troubleshooting.md#log-purge-unfinished). Topic changes add one `component=audit` line each (two `topic.alter` lines for a `PATCH` that failed part way), and a refused one (`outcome=denied`) is logged at warning level. Until the leader is upgraded, a forwarded change it lost its leadership over is still audited as `failed`: a 3.0.x leader's `503` does not say the change may still apply.
- **Schema validation bounds during a rolling upgrade.** The new registration checks run on the Raft leader: until it is upgraded, a 3.0.x leader still registers a schema an upgraded one refuses (a costly pattern, more than 64 validation paths), and annotation-only changes still add versions. The depth limit, enum hashing and the validation bound apply on each upgraded node to every produce it validates, whichever leader registered the schema, so during the roll a deep payload is `400` on an upgraded node and accepted on a 3.0.x node. Nothing stored changes format, and a schema registered before the upgrade is never re-checked: one that the new checks would refuse keeps working and is validated under the validation bound. A rollback needs no step.
- **New refusals clients can see (schemas).** `400` for a produce body nested deeper than 256 levels and for a schema whose validation would cost too much; `503` for a produce when the node's validation bound stayed full for 5 s (Narad answered no produce with `503` before); `409` for a schema write past a byte budget. A client or test that told schema versions apart only by `title` or `description` must change a validation keyword instead.
- **Schema histories already over a byte budget.** 3.0.x let a topic store up to 1000 schema versions of 256 KiB each, so a topic can come out of the upgrade with a stored history over the new 4 MiB budget, and a cluster with more than 256 MiB of schemas, fan-out children's copies included. Nothing stored is removed or rewritten, and produce and consume go on as before. But such a topic takes no new schema version (re-sending its current schema, or an annotation-only edit, still answers `200`) and no new schema-less fan-out child, by attach or create-as-child, since the child would copy the whole history; on a cluster over 256 MiB no topic takes a new schema version, a create with a schema or a schema-less child of a topic with a schema until topics are deleted to bring the total under the budget. The `409` says the history is already over the budget and names the way out: put the new schema on a new topic and move producers and consumers to it. Until the Raft leader is upgraded, a 3.0.x leader still accepts versions past the budgets. To find such topics before you upgrade, sum each topic's history: `curl -s -u "$AUTH" "$NARAD/v1/topics/<topic>/schema" | jq '[.versions[].schema | tojson | utf8bytelength] | add'`, for every topic `GET /v1/topics` lists (page with `page_token`); the sum over every topic is the cluster total. That counts the compacted schemas, and a version stored with whitespace holds more, so treat a topic above about 3 MiB as at risk.
- **Metadata database.** `fsm.db` gains an `fsm_meta` bucket (the applied index, the transaction that wrote it, the newest entry type applied) that 3.0.x ignores, in its own file and in the Raft snapshots it installs, so a mixed-version cluster needs nothing. The first restart on this release of a node with no Raft snapshot yet rebuilds `fsm.db` from the Raft log and keeps the old file as `fsm.db.stale` (`metastore: set aside fsm.db as fsm.db.stale and rebuilding it from the raft log`, warning; delete the file once the node is ready). The rebuild costs one synced write per log entry, what 3.0.1 paid on every restart; a node with a snapshot restores it instead, as before. A node rolled back to 3.0.x and upgraded again gets the same rebuild, or a snapshot restore, because 3.0.x writes the file without the index. A node whose Raft state is gone (`raft.db` and the snapshots deleted) beside an `fsm.db` that holds anything sets the file aside the same way when it joins a running cluster, whose log or snapshot rebuilds it. A node that would bootstrap a new cluster instead (a single node, or an initial member none of whose peers answers) refuses to start with `holds metadata, but there is no raft state beside it` and leaves the file untouched, where 3.0.1 replayed the new log onto it: restore `raft.db`, the snapshots and `fsm.db` from the same backup (copy the `topics` directory first, since the node removes the directories of topics created after the backup as orphans), or move `fsm.db` away to start the node empty (see [Troubleshooting](docs/operate/troubleshooting.md#log-metastore-no-raft-state)). Restoring `raft.db` alone does not get past it: a node whose Raft log and snapshots end before what its `fsm.db` holds (they came from a backup and `fsm.db` did not) refuses to start with `raft state is older than fsm.db`, naming both indexes, and leaves the file untouched, where 3.0.1 replayed the older log onto it or restored the older snapshot over it; a node that joins a running cluster sets the file aside instead (see [Troubleshooting](docs/operate/troubleshooting.md#log-metastore-raft-state-older)).
- **Full disks.** A node whose metastore cannot write now stops with an error and restarts in a loop until space is freed, where 3.0.1 silently dropped the change on that node. Nodes that share a full volume all stop: keep free space on the data volume and alert on it. The lines worth an alert are `metastore: stopped applying raft entries` (error) and `metastore: could not write raft entry` (warning).
- **Metastore snapshots.** A Raft snapshot of the metadata database first copies `fsm.db` to `fsm.db.snapshot-<random>` beside it, so keep free space on the data volume equal to `fsm.db`'s size (`narad_metastore_fsm_bytes`) on top of Raft's two snapshot files. Without it the snapshot fails (logged at error, counted in `narad_metastore_snapshot_failures_total`), Raft tries again at its next interval, and its log grows until one succeeds. The snapshot itself is the same bbolt image as before, so v3.0.1 and this release install each other's snapshots, during a rolling upgrade and after a rollback. A copy left by a crash is deleted at this release's next start; v3.0.1 does not know the file, so after a rollback delete any `fsm.db.snapshot-*` file in the metastore directory by hand.
- **Scale-out and decommission during a rolling upgrade.** A leader on 3.0.x admits a joiner as a voter at once, as before, and promotes a staged non-voter as soon as it asks again. A node that joins while it runs 3.0.x is staged by a leader on this release and stays a non-voter (3.0.x never asks for promotion) until it runs this release and restarts, then asks itself; it replicates and serves meanwhile. The `421` and `200` join bodies only gain fields, which a 3.0.x joiner ignores while it walks its pinned peers as before. A 3.0.x leader removes only voters when a decommission completes, so a non-voter decommissioned under it loses its member record but stays in the Raft configuration, heartbeated by the leader and counted in `narad_raft_nonvoters`; finish the upgrade before decommissioning a non-voter. To remove one left behind that way, start its pod with an empty volume so it is readmitted under its ID, then decommission it again under this release. A rollback keeps any staged non-voters in the configuration, replicating as before. Under 3.0.x one is promoted only if it goes 15 s without a leader and its join loop asks again, and a 3.0.x decommission leaves it in the configuration. The joiner's `cluster join rejected` and `cluster join refused` lines carry `via` (the address that answered) instead of `peer`, and the leader's `join cluster: add voter` error is now `join cluster: admission failed`.
- **Raft entry types and rollbacks.** Heartbeats and joins carry new trailing fields (the build and the newest Raft entry type a node applies). A 3.0.x leader refuses them with a `400`, and an upgraded node resends them without the fields at once, so a rolling upgrade needs no step and no member misses a heartbeat window. A 3.0.x replica drops the new member fields from its copy of the record, which only makes the check stricter while it leads. Once every member has run a release that adds a Raft entry type, rolling back to a release that lacks it is unsupported, whether or not that type has been used yet (see the next note): 3.0.x skips such entries silently, and 3.1.0 and later stop with an error instead. Roll back only before that point, and never add a node running an older release to a fully upgraded cluster (it is refused with `409`, code `older_release`; a 3.0.x joiner logs that as `cluster join refused: this node was decommissioned`, with `older_release` in its `body`).
- **New Raft entry types: the rollback boundary.** This release adds nine metadata (Raft) entry types, numbered 23 to 31, for the topic and placement fixes above: single-entry topic creates, compare-and-set topic alters, schema changes, deletes, attaches and detaches, insert-only placement, the orphan assignment row prune, and dead marks that carry a heartbeat. The leader starts using them only once every member, including members marked dead and Raft servers without a member record, reports a release that applies them; until then it writes the entries 3.0.x applies, and those fixes do not apply yet (this release's leader-side checks still do). While a member holds them back, the leader logs `metastore: not using a new raft entry type yet; proposing the entries every member applies` at info, at most once a minute per type, naming the member, and logs each orphan assignment row once at error (`orphan assignment row for <topic>/<partition>; it is pruned once every member runs 3.1.0`). It logs the first use of each type once at info, for example `metastore: every member applies raft entry type 23; using create topic with schema and link`. From that line on, a 3.0.x binary must not run in the cluster: it would skip the new entries silently and serve a diverged copy of the metadata. So do not roll back to 3.0.x once every member has run this release, even if that line was never logged: a node stopped to roll it back keeps counting as this release while it is down (its member record holds its last report), so the leader can use a new type in that time, for example to mark it dead after 30 s of silence or for a topic create. 3.1.0 and later stop with an error on an entry type they do not know instead. One new answer reaches clients: `409` `topic changed since it was read`, when a topic changed twice under one request.

## [2.2.0] - 2026-09-06

### Added
- Schema support end to end: a schema history endpoint, `schema` and `schema_version` on topic details, idempotent re-registration, an optional base version so racing registrations get a 409, a 1000-version cap, CLI `--schema` support, and a Schemas page on the documentation site.
- Read-your-writes on forwarded control-plane writes: a topic, user, schema, or fan-out change sent to a follower is applied there before it answers, so an immediate read or produce on the same node sees it.
- A consume waiting on one partition owner now also sees a message that lands on another owner during the wait.

### Changed
- Forwarded consumes no longer serialise on a per-call scan of delivery records; acks on a 3-node devstack went from 29.6k/s to 48k/s mean with even broker CPU.
- Fewer syscalls and copies on produce, consume, and ack: positional writes, reused frame buffers, held-open watermark and checkpoint descriptors, buffered WAL replay, targeted consumer wake-ups, and a cached owned-partition list.
- `GET /v1/topics/{topic}` no longer opens idle partition logs and fetches remote partition stats concurrently.
- Cluster RPC moved bulk traffic onto its own lanes, detects restarted peers immediately, and hands a message back when a forwarded long poll's client leaves.
- The Helm chart pins the peer list to the initial cluster size, so raising `replicaCount` no longer restarts every pod; PDB `maxUnavailable` is 1 and a silent scale-in is refused.
- The CLI pools connections with drained bodies and spreads them across every address the broker name resolves to.
- A mixed-version cluster now needs `security.allow_legacy_cluster_auth: true` on the upgraded nodes during the roll, because the cluster RPC handshake changed.
- Dependency bumps (quic-go 0.62, x/crypto 0.55, klauspost/compress 1.19.2, prometheus client 1.24.1, jsonschema 6.0.3) and a Go 1.27 modernizer sweep.

### Fixed
- A committed message could stay hidden after a crash until the partition's next commit; the high watermark is now persisted before the batch is exposed.
- A node restarting with a lagging Raft replica could take ownership of partitions reassigned while it was down and lose the records; ownership reads now wait until the replica has caught up with the leader, and `/readyz` is a live check that flips back when the leader is lost.
- Partition moves carry the fan-out cursor files, so rebalancing or decommissioning a parent partition no longer drops a child's backlog (for a delay child, its entire pending window).
- A handoff reports the consumer frontier after draining in-flight leases, so the new owner no longer redelivers the last acked messages, and the handoff freeze is fenced by a token the flip must present.
- A topic deleted and recreated under the same name can no longer resurrect the old incarnation's data.
- One lost ack no longer made a partition crawl at one batch per visibility timeout: the acked-ahead cap gates fresh deliveries only, acks for already-delivered messages are always accepted, and long pollers wake when an expired lease frees the frontier.
- Fan-out cursors anchor exactly at the attach point (and at offset 0 for partitions added later), so records committed between an attach and the cursor's first read are delivered.
- A node that received a partition back inside the freeze window of a move it had just sourced no longer refuses every commit for about a minute after a join-then-decommission cycle.
- A failed commit followed by the dispatcher's retry no longer delivers the batch twice, fsync errors poison the log until reopen instead of being retried, retention now bounds record lifetime for low-volume topics through a time-based segment roll, and data files are created 0600.
- Schema versioning is driven by the persisted history and fails closed, so a leader whose registry never loaded a topic can no longer overwrite v1, and every node picks up a schema registered elsewhere.
- A move's destination no longer serves stale files (and loses later writes) when it still held the partition's log open from an earlier ownership.
- Reservations are released on transient read errors, a consumer behind retention jumps to the oldest offset in one step, and moves of idle partitions or moves whose target died no longer pin the cluster.

### Security
- Cluster members and moves are admin-only, attaching a child requires manage rights on the child as well, and topic reads require a grant on the topic (the topic list is filtered).
- Cluster peers prove the shared secret bound to the TLS session in both directions; the previous fixed token was replayable and servers were never authenticated.
- User updates are field-scoped Raft operations, so a password change proposed from a stale replica can never resurrect revoked grants; passwords over 72 bytes are rejected with 400.
- Raft requires TLS when security is on unless plaintext is explicitly allowed, and pre-auth frames, segment chunk reads, and the transfer and control RPCs all gained size bounds.
- HTTP gained header and connection caps, a per-identity in-flight consume cap, a required JSON or octet-stream content type (or the `X-Narad-Client` header) on state-changing requests, and `/metrics` on its own listener or behind auth; the CLI gained `--password-stdin`.
- Decommissioned members are removed from membership and cannot be resurrected by heartbeats, and a removed or state-less initial member joins instead of bootstrapping a rival cluster.

- The produce dispatcher no longer discards accepted, durable, undelivered records when the topic is missing from a stale local metastore replica; discard now also requires a caught-up replica and leader confirmation.
- A freshly elected leader no longer trusts its still-replaying state machine: every destructive action that treats local state as authority now runs a Raft barrier and re-reads first, and consumer offsets recover lazily from the per-partition file.

## [0.2.0-beta.2] - 2026-07-08

*Pre-release.*

### Fixed
- A restarted node's startup orphan sweep could delete live topic data; a directory is now removed only when the leader confirms the topic is absent.
- Fan-out cursors could silently rewind to the tail and drop a delay backlog (about 2,000 lost deliveries were measured); tail-anchoring now requires leader confirmation of the attach epoch, and reconcile passes wait until the replica is caught up with fresh leader contact.

## [0.2.0-beta.1] - 2026-07-07

*Pre-release.*

### Added
- Topic fan-out: a parent topic replicates every message into up to 108 independent child topics, preserving per-key ordering within a child under an at-least-once contract, with detach and re-attach guarded by attach epochs.
- Delay children: attach a child with `delay_ms` and each record is delivered only once the parent's commit time plus the delay has passed, giving retry-backoff tiers and scheduled reprocessing from one flag.
- Ack lease operations: `extend` renews the visibility window on the same receipt handle and `extend=0` is a NACK for immediate redelivery, with a lapsed lease returning 410.
- A keyed record envelope: consumers now receive the produce key and the real commit timestamp.
- CLI `topics attach/detach/children` and `ack --extend/--nack`, plus fan-out, delay, and ack lease metrics.

### Changed
- Every topic now has a uniform one-hour retention floor, which backs the fan-out and delay buffer guarantee.
- Breaking: the partition-log record envelope changed, so pre-beta partition data does not decode and topic data must be wiped when upgrading from any alpha build; the attach and detach cluster RPCs also changed shape.

## [0.1.0-alpha.2] - 2026-07-06

*Pre-release. The security milestone of the 0.1.0 line.*

### Added
- HTTP API authentication over a bcrypt-hashed user store with a per-node verification cache, and a root admin seeded at first boot.
- RBAC with produce, consume, create, and admin grants over literal or prefix-wildcard topic patterns, plus a user-management API with no-privilege-escalation invariants.
- Topic ownership: the creator owns a topic, and only the owner or an admin may alter or delete it.

### Security
- Narad is secure by default; existing unauthenticated clients receive 401 after upgrade unless security is explicitly disabled.
- The node-to-node QUIC transport requires a shared-secret HMAC handshake per stream, and the Raft metadata transport gained optional mutual TLS.
- A pentest on a live cluster held 44 of 44 designed invariants; the single finding (public `/metrics` exposure through the ingress) was fixed.

### Fixed
- A 40-bug correctness pass across storage, WAL, cluster, and broker.
- arm64 images now contain arm64 binaries; previously every arm64 image shipped an amd64 binary and crash-looped.

### Removed
- The inert `SyncBytes` knob (strict config decoding now errors on the removed key), and debug-only metrics were pruned to the operator-useful set.

## [0.1.0-alpha.1] - 2026-06-27

*Pre-release.*

### Added
- Narad's first alpha, published for early evaluation, local development, and design review, with a container image on GHCR. The remaining production-readiness gates (API auth, rate limiting, TLS, and a tested durability and disaster-recovery contract) were documented as still open.
